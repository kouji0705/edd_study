# Pokémon Battle Event-Driven Design

ポケモンバトルを題材に、**イベント駆動設計（Event-Driven Design）** を学習するためのリポジトリです。

TypeScriptを使い、バトルシステムを段階的に実装しながら、Section・Event・EventHandlerの役割や、処理の割り込み・連鎖について理解を深めていきます。

## 現在の状態

Step 5（実行順序の管理）を実装済みです。`npm start` はリザードン対ピカチュウを表示します。ハンドラなしの `runBattle()` と、せいでんき成功の連鎖は Step 4 と同じ結果です。

- このREADME：学習全体の方針とロードマップ
- [Step 1の設計書](step1.md)：1ターンの仕様、処理図、期待結果、テストケース
- [Step 2の設計書](step2.md)：Sectionの階層、入出力、テストケース
- [Step 4の設計書](step4.md)：せいでんきとクラボのみの割り込み
- [Step 5の設計書](step5.md)：ハンドラの優先度、スタックとキュー
- 実装：`src/main.ts` と `src/battle/`
- テスト：`tests/step1.test.ts`、`tests/step2.test.ts`、`tests/step3.test.ts`、`tests/step4.test.ts`、`tests/step5.test.ts`

## 実装の責務

`battle.ts` と `scenario.ts` は、ポケモン構成・技選択・ハンドラ登録を決めます。共通の開始・登場・ターン実行は `battle-flow.ts` にまとめ、実行のたびに新しい状態を作ります。ポケモン検索と名前の定義は `pokemon.ts` に置き、攻撃・状態異常・特性から参照します。

`section.ts` は実行順と上限を管理します。ターン境界は表示名ではなく `Section.scope: "turn"` で宣言し、Runner が計測の開始・終了と再入禁止を担当します。Section は必ず Runner 経由で実行します。`turn.ts` はターン内の処理の組み立てを担当します。

## 背景

趣味でポケモンバトルのシミュレーターを開発している中で、特性・持ち物・技の追加効果など、複雑な仕様の実装に難しさを感じました。

そこで、ゲームフリークがCEDEC2026で紹介したバトルシステムの設計を参考に、イベント駆動設計について学習することにしました。

最初から完成度の高いバトルシミュレーターを作るのではなく、小さな機能を実装しながら、設計が必要になる理由を理解することを目指します。

## 学習目標

- イベント駆動設計の基本的な考え方を理解する
- Sectionによる処理の構造化を理解する
- EventとEventHandlerによる責務の分離を理解する
- 複雑な割り込みや処理の連鎖を実現する
- イベントの実行順序や状態管理の方法を学ぶ

## 用語と学習用の前提

以下は本リポジトリで使う作業上の定義です。公開講演の内部実装やAPIを規定するものではありません。

| 用語 | 本リポジトリでの役割 |
| --- | --- |
| Section | 攻撃や状態異常付与など、一連の処理をまとめる実行単位 |
| Event | Sectionの処理中に発生する通知。種類、発生元、対象などの情報を持つ |
| EventHandler | Eventを受け取り、適用条件を判定して個別の効果を処理するもの |

まずは単一プロセス内で同期的に処理します。ネットワーク配信や非同期メッセージ基盤は対象外です。実行ログは処理順序の検証に使うもので、Eventそのものや状態復元用の履歴とは区別します。

各Stepで採用するバトル条件は学習用の簡略化です。実際の作品に準拠する範囲を広げる場合は、対象作品と対応するルールを別途明記します。

## 学習ロードマップ

### Step 1：バトル開始からターン終了までを実装する

まずは、最小限のバトル処理をTypeScriptで実装します。

**実装内容**
- バトル開始
- ポケモン登場
- ターン開始
- 行動選択
- 行動順決定
- 行動実行
- ターン終了

1対1・1ターン・固定20ダメージとし、両者の初期HPは100とします。特性や持ち物、ひんし・勝敗判定は扱いません。詳細は[Step 1の設計書](step1.md)を参照してください。

**確認条件：素早さ順に各1回攻撃し、両者のHPが80、ターン番号が1になること。**

**学習目標：バトル全体の処理の流れを理解する**

### Step 2：Sectionによる構造化

Step 1で作成したバトル処理を、役割ごとにSectionへ分割します。

- Sectionの責務を定義する
- Sectionを階層的に組み合わせる
- Sectionの実行順序を管理する

詳細は[Step 2の設計書](step2.md)を参照してください。

**確認条件：Step 1と最終状態・処理順序が一致すること。**

**学習目標：ゲームロジックを構造化する方法を理解する**

### Step 3：EventとEventHandlerの導入

Sectionの処理中にEventを発火させ、個別の仕様をEventHandlerで処理します。

- Eventの定義
- EventHandlerの登録
- Eventの発火
- 特性や持ち物の効果を分離

この段階から、同じEventのハンドラは登録順に同期実行し、全ハンドラの完了後に発火元へ戻る、と定めます。登録はバトルごとに行い、実行中の登録・解除は扱いません。

通知は `executeAction` の中で、最終ダメージを決める直前と、HPを更新した直後に発火します。直前のハンドラが変更したダメージをHPへ反映します。特性や持ち物の具体的な効果は、まだ標準のバトルには登録しません。

**確認条件：ハンドラがない場合に既存結果を維持し、登録したハンドラが指定した通知箇所で1回ずつ実行されること。**

**学習目標：基本処理と個別ルールを分離する方法を理解する**

### Step 4：割り込みと連鎖

特性「せいでんき」と道具「クラボのみ」を題材に、処理の割り込みと連鎖を実装します。Step 1とは別の学習用シナリオを用意し、接触攻撃を受けた防御側の効果で、攻撃側にまひを付与し、攻撃側の持ち物で回復する流れを扱います。攻撃側はまひが有効な条件とし、発動判定はテストで成功・失敗を指定できるようにします。ここでは実際の発動確率や耐性ルール全体の再現は扱いません。

- EventHandlerからSectionを呼び出す
- 状態異常の付与
- 状態異常をきっかけにした道具の発動
- 割り込み後の処理への復帰

割り込み先を完了してから呼び出し元の次の処理に戻る、深さ優先の順序を採用します。まひは状態が変化したときだけ通知し、きのみは回復通知より前に消費済みにします。異常な循環に備え、1ターン内のSection実行数・Event発火数に上限を設け、超過時は原因をログに残してエラーで停止します。

詳細は[Step 4の設計書](step4.md)を参照してください。

**確認条件：まひ付与 → きのみ消費 → まひ回復 → 元の処理へ復帰の順序と、最終状態・持ち物消費が一致すること。発動失敗時や持ち物なしの場合も検証します。**

**学習目標：イベントによって別の処理が連鎖する仕組みを理解する**

### Step 5：実行順序の管理

複数のイベントが発生したときの実行順序を整理します。詳細は[Step 5の設計書](step5.md)を参照してください。

- EventHandlerの実行順序
- 優先順位
- スタックによる処理管理
- キューによる処理管理
- Step 4で導入した循環対策の検証

スタックとキューは同じ順序を生むものではありません。両者を比較し、割り込みは深さ優先を維持するなど、用途ごとに採用する順序を明記します。ハンドラの優先順位が同じ場合は登録順とし、同じ初期状態・入力・発動判定で結果を再現できるようにします。

**確認条件：複数ハンドラ・入れ子の割り込み・同順位・循環について、期待する処理列または停止条件をテストで検証すること。**

**学習目標：複雑なイベントの実行順序を管理する方法を理解する**

### Step 6：バトルシステムへの応用

これまで学んだ仕組みを使い、より実際のポケモンバトルに近い処理を実装します。

- 複数ターン
- ポケモン交代
- ひんし判定
- 天候やフィールド
- 特性や持ち物の組み合わせ

複数ターンへの拡張時には、先にHPの下限、ひんし後の行動可否、勝敗とバトル終了条件を定義します。その後に交代や天候を追加します。

**確認条件：先手の攻撃で後手がひんしになった場合に行動せず、決着後は次の行動・ターンへ進まないこと。追加ルールごとに回帰テストを設けます。**

**学習目標：イベント駆動設計を実際のバトルシステムに応用する**

## 学習方針

各Stepでは、以下の3つをセットで作成します。

1. **フローチャート**：処理の全体像を整理する
2. **TypeScriptコード**：実際に動くものを実装する
3. **実行ログ・テスト**：想定した順序で処理されていることを確認する

最初から複雑な仕組みを導入せず、必要性を理解してから設計を拡張していきます。

なお、本リポジトリはゲームフリークの内部実装を再現するものではなく、公開された設計思想を参考にした個人の学習プロジェクトです。
